# Test benchmark — 2026-09-25

Measured locally on Apple M3 Max, 16 logical CPUs, macOS 26.6.2 arm64, Node 24.5.0.
Base revision: `7c4e136e` plus the local eight-file mock migration. Runtime source was unchanged.
Browser 0.9.0 and Storage 0.8.0; Jest uses eight workers, fixture preparation/typechecking uses four processes.
The shared macOS arm64 runner enables `--no-sparkplug`. Browser launches and child CLI processes keep their normal flags.

## Method

Commands ran sequentially, outside the filesystem/network sandbox so HTTP fixtures could bind localhost.
One warm-up preceded three measured runs for each individual group. Caches stayed warm; fixture applications were rebuilt
where their commands require it. Full `npm test` and pre-push each ran once after the individual groups.
Wall time uses Python `time.perf_counter()` around the entire command, including startup, reporting and process exit.
Jest groups in the main series include `--json --outputFile=...`; their JSON/report overhead is included. Builds are excluded
from group-only Jest commands and included only in the build/full/pre-push rows. Coverage uses the existing Babel provider.

The raw [results](2026-09-25.json) include every command, warm-up, exit code, measured wall time, Jest-reported time,
and sum of per-file elapsed time where available. Per-file elapsed sums are **not CPU time**. All reported runs passed.
An initial restricted unit warm-up failed with `listen EPERM`; it was excluded and the entire before-series rerun outside
that sandbox. No test failures were retried within the reported benchmark series.

## Cost of the last eight-file migration

For a like-for-like check, the exact command `npm run test:unit` ran before and after these edits, without JSON reporting.
Both versions contain **135 suites / 1676 tests**. Each series has one warm-up and three measured runs:

| State                       | Median wall, s | Range, s  |
| --------------------------- | -------------- | --------- |
| Before local-mock migration | 4.58           | 4.45–4.68 |
| After local-mock migration  | 4.35           | 4.32–4.35 |

The observed change is -5.0%. Three runs do not establish a statistically significant speedup; they show
no observed slowdown for this migration. The separate JSON-report series was slower; do not mix those timings when
estimating the cost of the code changes or attribute the entire difference to the reporter.

## Historical comparison

The original user-provided measurements used a smaller test set and did not fully specify the command/reporting settings.
They are reference points, not a controlled A/B benchmark. The initial unit suite had 98 files / 1197 tests, while the final
suite has 135 files / 1676 tests. Build + types grew from 10 to 36 files; Chrome grew from 12 to 17 files.

| Group                       | Original wall, s | Final wall, s | Interpretation                                                  |
| --------------------------- | ---------------- | ------------- | --------------------------------------------------------------- |
| Package build               | 3.4              | 3.30          | Essentially unchanged                                           |
| Units, ordinary npm command | 8.3              | 4.35          | About 1.9× faster, with ~40% more tests                         |
| Units + Babel coverage      | 7.9              | 8.52          | No demonstrated speedup; final series includes JSON reporting   |
| Build + types               | 14.3             | 54.48         | Slower; expanded suite and current Relay declaration bottleneck |
| Chrome                      | 17.4             | 8.65          | About 2.0× faster with more files                               |
| Firefox                     | Not run          | 13.35         | No initial local baseline                                       |

Do not compare the old CI fixture step (54–60 s) directly with the new local 8.92 s: hardware, application count and build
inclusion differ. The old ~5-minute CI job also cannot be compared directly with local full-suite time. No current CI
performance measurement was made here. The initial report gives no comparable whole-hook timing. Pre-commit now checks
staged formatting only; timing it with an empty index would not represent a real commit, so no pre-commit figure is claimed.

## Remaining bottleneck

The later [Relay type-checking follow-up](2026-09-25-relay-types.md) isolates the expensive constructor inference,
records its fix and splits consumer responsibilities. The measurements below describe the pre-fix state.

In the three measured build/types runs, `RelayDeclaration.test.ts` took **52.26, 53.91 and 53.92 s**. The group finished
in **52.89–54.48 s**, so this file almost entirely determines its wall time. It constructs separate TypeScript programs
for source/package consumers and POSIX/Windows declaration paths. The next largest file, `override.integration.test.ts`,
took **21.95–22.82 s** and ran alongside it. More workers cannot shorten the longest file.

This benchmark does not establish the cause of the difference from the historical 6.5 s Relay declaration figure.
A separate optimization should profile program construction/type checking and investigate safe reuse or splitting of those
four consumer checks while preserving both public surfaces and path variants. This migration did not change that test.

## Reproduce

From the repository root, run each individual command once to warm up and then three times, sequentially. Use an external
monotonic timer for wall time; append `--json --outputFile=<unique file>` to Jest commands to reproduce the main series.

```sh
npm run build
npm run test:unit
node scripts/test-run.mjs --selectProjects unit-node unit-dom --coverage --coverageProvider=babel
node scripts/test-run.mjs --selectProjects build types
node scripts/test-run.mjs --selectProjects chrome
node scripts/test-run.mjs --selectProjects firefox
node node_modules/tsx/dist/cli.mjs tests/integration/typecheck.ts --prepare
npm run test
npm run test:pre-push
```
